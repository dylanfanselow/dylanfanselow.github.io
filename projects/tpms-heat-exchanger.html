TPMS heat-exchanger capstone

Capstone · 2026 · nTopology, SolidWorks, Ansys Fluent, Python

The project was "Optimizing the process of designing cooling-channel geometry using machine learning". I picked it up after the previous students had left, with nothing that ran end to end, and rebuilt it from scratch, starting with the geometry.

The project

TPMS lattices make excellent cooling channels: lots of surface area, smooth flow paths, and they can only be made by 3D printing. But each design has to be checked with a conjugate-heat-transfer CFD run that takes hours. The idea was to generate many lattice geometries automatically, simulate them, and train a surrogate model that suggests which geometry to simulate next, so you spend as few expensive CFD runs as possible.

When I took it over, the earlier team had gone. What was left was a set of single-case scripts and notebooks, a missing batch-geometry step, and boundary conditions that didn't agree between files.

What I did

Geometry and CAD

The geometry is the foundation of the whole pipeline. Every downstream step depends on getting a clean fluid domain and solid lattice with correctly labelled boundaries.

  • Built the TPMS cooling-channel geometry in nTopology, an implicit (field-based) modeller, so a design is a set of parameters rather than a hand-drawn part.
  • Set up the export as a fluid + solid surface-mesh pair, with boundary zones (inlet, outlet, chip wall…) tagged by name. Those names are the contract with the CFD stage.
  • Wrote the batch driver that turns a design space into one JSON input per geometry, runs nTop's command-line tool, and records a manifest of every case.
  • Started on hybrid and graded TPMS, which blend lattice families smoothly using a Shepard inverse-distance kernel.

Rebuilding the pipeline around it

  • Reorganised the project into four stages, each with its own folder and README: geometry → mesh and solve → ML → automation. One config.py holds the design space, boundary conditions, mesh sizing and solver settings, so changing the study is a config edit, not a code change.
  • Settled the boundary conditions on one canonical profile (mass-flow inlet, 300 K inlet, 350 K chip), the physics behind the validated 48-case dataset.
  • Defined what "done correctly" means at every stage. For example, every case must close its heat balance, and failures are logged instead of silently dropped. I also wrote onboarding docs so the next team can pick it up without starting over.
  • The ML stage already runs: it fits a Gaussian-process model to the seed data and suggests the next geometries to simulate.

What I learned

  • Inheriting a project is its own skill. Most of the early work was finding out what the old code actually did, which pieces were trustworthy, and what had to go.
  • Interfaces matter as much as the parts. A single misnamed boundary zone in the geometry breaks the CFD setup two stages later. Writing those names down as an explicit contract mattered more than any one script.
  • Write things down for the next person. The project stalled because knowledge left with the people. Documentation and a single source of truth for settings are what let it survive the next handover.
